## 2. Remaining issues, ranked by demo impact

1. **High:** the audit release is not deployed. Shared production still needs the coordinated
   module/frontend update described below. Its read-only check is not proof these fixes run there.
2. **Medium:** missions can end blocked or exhausted. The actual concurrent run verified defense
   and exhausted attack without capture. Model explanations sometimes describe a different
   approach from their structured action; the action field and measured receipt are authoritative.
3. **Medium for long sessions:** 200 turns per role is a database-lifetime admission cap.
   New Chat/reset does not replenish it. Archival/cap replenishment remains unimplemented;
   cancellation works at capacity. Retained history is intentional, bounded demo evidence.
4. **Low for this audit:** batching movement looks promising in a disposable benchmark, but is
   not implemented. The comparison changes cadence and lacks a representative smoothness test.
   GPU performance and long-running memory stability remain unverified on demo hardware.

## 4. Actual Bitdeer versus fixtures

`scripts/audit-maincloud-provider.ts --real`, using an authorized local environment key,
publishes only to a disposable local database. It runs the normal production WASM and fixed
Bitdeer HTTPS endpoint with 200 synthetic drones, original deadlines and unchanged call limits.
The key is installed as a private server environment variable, never in browser configuration.

The final credentialed run made **27 actual requests**: four coordinator requests (answer,
clarification and two plans), plus 23 specialist requests. Per-mission cumulative budgets were
15 and 10 calls, below 33. Recorded inference intervals peaked at four concurrent requests.
All reported `zai-org/GLM-5.3-Flash`; no fixture substitution or additional model was used.

Bitdeer responded to measured resisted preparation with a direct command, responded to blocked
entry with scheduled waits, and later retried after simulated state changed. Defense selected
preparation and repeated hardening as readiness changed. SpacetimeDB verified defense **2/2**;
attack finished **budget_exhausted, 0/2 capture objectives**, with measured partial access.
This demonstrates adaptation and honest terminal reporting, not guaranteed attacker success.

Timeout, refusal, malformed output and rate-limit mechanics are covered by injected fixture
errors/native parsing tests. They were not all induced against the live provider. The actual
initial malformed-output failure is separately retained as regression evidence. No new
credentialed mission was run against shared production.

## 5. Measurements and integration responsibilities

| Measurement | Conditions / result |
| --- | --- |
| Actual Bitdeer coordinator latency | Four calls: median 1,410 ms, maximum/p95 1,642 ms. |
| Actual Bitdeer specialist latency | 23 calls: median 852 ms, p95 1,255 ms. Reported usage across all 27 calls: 87,786 tokens. No alternate-model comparison or price estimate. |
| Reset stability | Before: pad 168 → 60 → 168. After: 168 throughout three local browser resets; garbage-collected JS heap 11,371,788 → 11,368,892 bytes. Short observation, not a soak test. |
| Renderer | Chromium/SwiftShader, 1440 × 900, all 200 drones, six-second sample: 16 draw calls, 101,306 triangles, 25.3 fps, p95 frame 50.1 ms, p95 draw submission 1.4 ms. Not hardware GPU evidence or a comparable before/after speed claim. |
| Scheduling experiment | Disposable standalone, 200 drones, one scoped subscriber, one-second warmup, five seconds per arm: independent schedules delivered 4,313 updates using 2.32 CPU seconds; experimental batching delivered 4,200 using 0.09 CPU seconds. Cadences differ. Neither comparison module nor batching is deployed. |

Bitdeer chooses intent, complementary assignments, typed goals, permitted actions, retargeting
and handoffs. Scoped observations, recent receipts, teammate assignments and remaining budgets
feed its subsequent decisions. It cannot authorize execution or certify success.

SpacetimeDB transactionally validates roles, assignments, current policy, epochs/generations,
admission, idempotency and budgets; atomically claims durable work; schedules and resolves
attempts once; creates evidence; and verifies terminal conditions. External HTTP runs outside
transactions and completion revalidates current authority. Independent movement continues.
Private typed assignment state is authoritative; compatibility views reconstruct existing UI
rows. Subscription synchronization reconstructs durable history on reconnect. The chat timer
reads the SDK's local cache; it is not network polling and was retained.
